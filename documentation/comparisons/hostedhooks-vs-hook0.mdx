# Hostedhooks vs Hook0

:::caution Hostedhooks is offline (checked 26 November 2026)
`www.hostedhooks.com`, its `/pricing` page and the bare `hostedhooks.com` domain all returned HTTP 503 with Heroku's "Offline for Maintenance" page on 24, 25 and 26 November 2026. The Heroku add-on listing still answers but is marked Alpha, the public docs say they were last updated five years ago, and the SDK repositories on GitHub have had no push since January 2023. We no longer list Hostedhooks in our comparison tables. This page stays up for teams that still run on it.
:::

Hostedhooks was a proprietary, hosted-only webhook platform: quick to set up, with a small feature set. Hook0 is open-source and does more on multi-tenancy, event routing, and self-hosting. The table below compares Hook0 with Hostedhooks as Hostedhooks documented itself before it went offline.

**Legend:** ✅ = Full support | ⚠️ = Partial support | ❌ = Not available

## Open-source vs proprietary

This was the main difference, and it is now the practical one. With Hostedhooks:

- You can't inspect the source code
- You can't self-host it
- You can't customize the behavior
- When the service goes offline, as it has since November 2026, you have to rebuild or migrate
- You have no visibility into how your data is processed

With Hook0:

- Full source code under SSPL-1.0
- Self-host on your own infrastructure with zero feature restrictions
- Fork and customize if needed
- The only restriction: if you offer Hook0 as a managed service to others, you must open-source your entire stack
- Your infrastructure runs independently of Hook0 the company
- Audit every line of code that touches your data

In regulated industries (finance, healthcare, government), self-hosting and code auditing are requirements.

## Where Hook0 goes further

Hostedhooks covered the basics: send a webhook, check delivery, retry on failure.

Hook0 adds:

- **Event type hierarchies**: events organized as `order.created`, `order.updated`, `order.cancelled` instead of flat strings
- **Label-based filtering**: route events to subscriptions based on arbitrary key-value labels (useful for multi-tenant SaaS)
- **Dead letter queue**: failed events are kept for inspection and replay, not silently dropped
- **Biscuit token authentication**: capability-based access control with Service tokens for programmatic access, instead of all-or-nothing API keys

## Moving off Hostedhooks

If your producers still call the Hostedhooks API, the move to Hook0 maps one to one:

- **Event types**: recreate them in Hook0. Flat names work as is; you can switch to dot notation (`order.created`) later.
- **Endpoints**: each Hostedhooks endpoint becomes a Hook0 subscription, filtered by event type and, for multi-tenant setups, by labels.
- **Signatures**: receivers switch their HMAC check to the subscription secret Hook0 generates.
- **Sending**: point your producers at Hook0's `POST /event` API. Run it on [Hook0 Cloud](https://www.hook0.com) or [self-host it](/self-hosting/docker-compose) so the next shutdown is not someone else's call.

## Pick Hook0 if

- You need self-hosting (compliance, data sovereignty, air-gapped environments)
- You're building a multi-tenant SaaS platform
- You need event routing and filtering beyond flat event types
- You want open-source with no vendor lock-in
- You need dead letter queues and manual replay
