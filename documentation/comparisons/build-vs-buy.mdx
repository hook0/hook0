# What does it cost to build webhook delivery yourself?

Every engineering team that sends webhooks eventually asks whether to build the delivery layer or use a service. This page is the worksheet for that decision: every component of a production webhook sender, the hours to plan for each, the formula that turns them into a budget, and the concrete behavior Hook0 ships for each one, so you know the bar an in-house version has to clear.

For the short product overview of the same question (time to production, maintenance, lock-in), see [Build vs Buy Webhooks](https://www.hook0.com/build-vs-buy-webhooks) on hook0.com. This page goes one level down.

## Component breakdown

Webhook delivery is not just "make an HTTP POST when something happens." Here's every component you'll end up building. The hours are a planning baseline for a first production version by an engineer who knows the stack, not a measurement: replace them with your own estimates.

| Component | What It Involves | Planning hours |
|-----------|-----------------|----------------|
| **HTTP delivery engine** | Queue consumer, connection pooling, timeout handling, redirect following | 40h |
| **Retry logic with backoff** | Retry schedule, jitter, retry limits, per-endpoint state | 32h |
| **Signature generation** | HMAC-SHA256 signing, key rotation, multiple signature schemes | 16h |
| **Dead letter queue** | Failed event storage, inspection API, manual replay, retention policy | 32h |
| **Event type system** | Type hierarchy, schema validation, versioning | 24h |
| **Subscription management** | CRUD API, URL validation, filtering rules, enable/disable | 24h |
| **Delivery logging** | Request/response storage, timing data, searchable history | 24h |
| **Dashboard UI** | Event browser, delivery status, replay controls, subscription management | 80h |
| **Monitoring & alerting** | Success rate tracking, latency metrics, endpoint health | 32h |
| **Multi-tenant isolation** | Per-tenant rate limits, data isolation, access control | 40h |
| **API authentication** | Token management, scoping, rotation | 24h |
| **Circuit breakers** | Per-endpoint failure tracking, automatic slow-down and re-enable | 16h |
| **Rate limiting** | Per-endpoint and global rate limits, backpressure | 12h |
| **Total** | | **396h** |

## Turn the hours into a budget

The formula is short:

```text
first version = component hours × fully loaded hourly rate
yearly upkeep = (on-call hours + maintenance hours per month) × 12 × rate
```

With the 396-hour baseline, that is roughly 10 engineering weeks. At an example rate of $150 an hour, fully loaded, the first version comes to $59,400 before any upkeep. Put your own rate in: the order of magnitude is what matters for the decision, and it rarely changes the answer.

Two inputs teams tend to leave out of the upkeep line:

- **Who owns it in 18 months.** The engineer who built the retry queue moves teams, and whoever inherits it learns it during an incident.
- **What your customers compare you to.** Once they have integrated webhooks from Stripe or GitHub, they expect retries, signed requests and a delivery log they can read. The bar is set outside your company.

## The behavior you would have to match

The hour column above prices the components. This section lists the defaults Hook0 runs for the trickiest ones, so you can check an in-house design against a working implementation rather than a blank page.

### Retry schedule

Hook0 retries a failed delivery after a fixed sequence of growing delays:

| Failed attempts so far | Delay before the next attempt |
|---|---|
| 1 | 3 seconds |
| 2 | 10 seconds |
| 3 | 3 minutes |
| 4 | 30 minutes |
| 5 | 1 hour |
| 6 | 3 hours |
| 7 | 5 hours |
| 8 and beyond | 10 hours |

A delivery gets up to 24 retries (`MAX_RETRIES`) inside an 8-day window (`MAX_RETRY_WINDOW`). Each delay gets a random spread of up to 10%, at least 2 seconds and at most 15 minutes, so a recovering endpoint is not hit by a wall of retries in the same second. The full decision process is in [Webhook retry logic](/explanation/webhook-retry-logic).

### Signature format

Every request carries an `X-Hook0-Signature` header:

```text
X-Hook0-Signature: t=1765443663,h=content-type x-custom-header,v1=85da0586ae0b711d...
```

`t` is the Unix timestamp, `h` the space-separated names of the signed headers, and `v1` the hex HMAC-SHA256 of the timestamp, the header names, the header values and the payload. Signing the timestamp lets receivers reject replays, and signing headers stops an attacker from swapping them. Your version also needs secret rotation and verification code for each language your customers use. See the [security model](/explanation/security-model) and the [webhook authentication tutorial](/tutorials/webhook-authentication) for Python, Node.js and Go samples.

### Dead letters and replay

When retries run out, Hook0 keeps the last request attempt in the failed status, next to the event payload and the response the endpoint sent back. There is no separate queue to run: you list failed attempts, fix the endpoint, then replay the event with `POST /events/{event_id}/replay`. Details in [Where do webhooks go after the last retry?](/explanation/webhook-dead-letter-queue).

### Endpoint health

The circuit breaker row is where in-house systems most often cut corners. Hook0 can classify each subscription every 5 minutes from the attempts of the last 15 minutes: at least 10 attempts with more than 30% failed marks it unhealthy. A degraded subscription receives at most 50 attempts per minute and its retries wait at least 1 hour, without losing any of them. Self-hosted instances turn this on with the subscription health settings, which are off by default. See [subscription health](/explanation/webhook-retry-logic#subscription-health).

## The costs you don't plan for

The 396 hours above gets you to "it works." Then production traffic arrives.

### Ongoing maintenance

- Queue infrastructure monitoring and scaling
- Database growth management (delivery logs accumulate fast)
- Security patches for HTTP client libraries
- On-call rotation for delivery failures
- Schema migration when you add features

### Edge cases you'll discover in production

- Endpoints that accept the connection but never respond (slow loris)
- Endpoints that return 200 but with an error body
- DNS resolution failures that are transient vs permanent
- TLS certificate issues on customer endpoints
- Redirect loops
- IPv6-only endpoints
- Endpoints behind CDNs that cache POST requests (yes, this happens)

### Opportunity cost

Every hour on webhook infrastructure is an hour not on your product. For a startup, 10 weeks of engineering time can be the difference between shipping a feature that wins a deal or not.

## Build your own if

- You need custom protocols beyond HTTP, delivery to message queues, or non-standard auth
- You process billions of events daily and have the team to operate custom infrastructure
- Webhooks are your core product (if you're building a webhook platform, obviously build it)
- Regulatory requirements prohibit third-party services (though Hook0 self-hosting works in air-gapped environments too)

## Pick Hook0 if

- You want to ship webhook support this week, not next quarter
- You'd rather maintain your product than your infrastructure
- You need self-hosting without building from scratch
- You're a small team: you don't have 10 engineering weeks to spare and you don't have the ops capacity for custom infrastructure

## Moving off a homegrown sender

If you already run a homegrown system (a queue consumer with a retry table, for example), you do not need a big-bang cutover:

1. Create the event types and subscriptions in Hook0 through the REST API, one customer or one event type at a time.
2. Send each new event to Hook0 and to the old system in parallel, and compare the delivery logs.
3. Give customers the new signature header and its verification code, then switch off the old sender for them.

## Start with Hook0, migrate if needed

Hook0 is open-source (SSPL-1.0). If you outgrow the hosted service:

1. Self-host Hook0 on your own infrastructure
2. Fork and customize if you need specific behavior
3. Use the codebase as a reference implementation if you decide to build from scratch

You're not locked in. The code is there. The API is documented. See the [Getting started tutorial](/tutorials/getting-started) to send your first webhook.

## FAQ

### How do I estimate the cost of building webhook delivery in-house?

List every component you need, put an hour estimate on each, and multiply the total by your fully loaded hourly rate. Then add the recurring hours: on-call, log retention, security patches and the edge cases production traffic brings. The worksheet above uses 396 hours as a planning baseline for the first version.

### What retry schedule should an in-house webhook sender use?

Hook0 uses 3 seconds, 10 seconds, 3 minutes, 30 minutes, 1 hour, 3 hours and 5 hours, then 10 hours for every later retry, with up to 24 retries inside an 8-day window and a random spread on each delay. If you build your own, that is the behavior your customers will compare you to.

### What does an in-house webhook signature need to cover?

At minimum an HMAC-SHA256 over a timestamp and the raw body, so the receiver can reject both forged and replayed requests. Hook0 also signs a chosen list of headers. You also need secret rotation and verification samples for each language your customers use.

### Can I start with Hook0 and move to my own system later?

Yes. The server is open-source under SSPL-1.0, so you can move from Hook0 Cloud to a self-hosted instance with the same API, fork it, or read it as a reference implementation if you decide to build.
